## 1. 何を解決するか

**使命と、日々のクエストが繋がっていない。**

```text
【いま】
  ⚔ 使命        「読書を続ける」        毎日チェックを押すだけ
                                        ↑ 押しても何も起きない。ただのメモ
  📋 クエスト    5分だけ始める
                 1セッションを終える     ← 全員同じ固定3件
                 今日の自分をほめる

  この2つは、コードの上でも完全に別々（quests.js と boot.js で無関係）
```

使命は「決めた」だけで終わっていて、**今日なにをすれば近づくのかが分からない**。
クエストは全員同じで、**その人が何を目指しているかを知らない**。

この仕様は2つを1本の線にする。

```text
【あと】
  使命「読書を続ける」
    ↓ どうなれば達成か（KPI）
  週3日 × 25分
    ↓ 今週の残りから逆算
  今日の一手「読書で25分」
    ↓ クエストの文言に反映
  📋 読書で1セッションを終える  ⚔使命
    ↓ どの状態でも
  🧚 妖精が優しく声をかける
```

### やらないこと（スコープ境界）
- **「断ちたい習慣」は対象外**。あれは「やらなかった日数」で測るもので、
  回数×時間では測れない。仕組みが別なので、まとめて作らない
- **クエストを増やさない**（§4 で理由を数字とともに示す）
- **新しい localStorage キーを増やさない**（`gq_mission` の中に収める。掟4の手続きが不要になる）

## 2. M-1：使命にKPIを持たせる

### 2.1 データ構造（既存データを壊さない）

いまの `gq_mission` は `{ build: [{text, done}], quit: [...] }`（[boot.js:1547](../scripts/boot.js:1547)）。
**`build` の各要素に `kpi` を足すだけ**にする。

```javascript
{
  text: '読書を続ける',
  done: false,            // 既存。その日のチェック（毎日リセット）。触らない
  kpi: {                  // 追加。無い＝未設定。既存データはこのまま動く
    genreId:     'g_reading',  // どのジャンルの集中を数えるか
    daysPerWeek: 3,            // 週に何日やれば達成か
    minsPerDay:  25,           // 1日あたり何分で「1日」と数えるか
  }
}
```

> ⚠️ **`kpi` が無い既存の使命を壊さないこと。** 未設定として扱い、
> カードに「どうなれば達成か決める」ボタンを出すだけにする。
> **勝手に既定値を入れない**（ヨージが決めていない目標を押しつけることになる）。

### 2.2 なぜ「週3回」ではなく「週3日」なのか

**既存データで数えられるのが日数だから。**

```text
data.historyDetails['2026-08-05'] = {
  sessions: 3,                    ← 1日の合計回数。ジャンル別ではない
  genres: { g_reading: 50, ... }  ← ジャンル別は「分」しか持っていない
}
```

ジャンル別のセッション回数は記録されていない。**「読書で3回」は今のデータでは数えられない。**
記録形式を変えると既存ユーザーの履歴に手を入れることになるので、やらない。

代わりに「**その日、読書を `minsPerDay` 分以上やったか**」で1日と数える。
習慣の目標としても「週3日読書する」のほうが自然で、
「1回を短く刻んで3回にする」という抜け道も生まれない。

### 2.3 KPIの決め方（選択式＋自由記入）

**選ぶだけで決まるのが既定。自由記入も選べる。**
ここで入力に手間がかかると、使命が空のまま放置される。

```text
📚 どのジャンル？    [📖 学習] [🗣️ 英語] [📚 読書] …  ← 既存ジャンルから選ぶ
🗓 週に何日？        [1日] [2日] [3日] [5日] [毎日] [自分で決める]
⏱ 1日どれくらい？   [10分] [25分] [50分] [自分で決める]
```

- 「自分で決める」を押したときだけ数値入力を出す
- 既定の選択は **週3日 × 25分**（ポモドーロ1回ぶん）
- ジャンルが1つしかない人は、ジャンル選択を出さずにそれを使う

### 2.4 進捗の数え方

**週は月曜起点。** 週次レビューと同じ区切りを使う
（[calendar-review.js:676](../scripts/calendar-review.js:676) `dowIndex` が Mon=0 とする定義。
[1237行](../scripts/calendar-review.js:1237) の `_weekGenreMins` も月曜から7日ぶん数えている）。

> ⚠️ **週の区切りを自分で定義しないこと。** ここで日曜起点にすると、
> 週次レビューと使命で「今週」がズレる。GQ最頻出のバグ（データと画面のズレ）と同型。

```javascript
// 今週、KPIを満たした日が何日あるか
function missionWeekProgress(kpi) {
  const mon = mondayOfThisWeek();           // 既存の週の求め方に合わせる
  let days = 0;
  for (let i = 0; i < 7; i++) {
    const d = new Date(mon); d.setDate(mon.getDate() + i);
    const mins = data.historyDetails?.[dateKey(d)]?.genres?.[kpi.genreId] || 0;
    if (mins >= kpi.minsPerDay) days++;
  }
  return { days, target: kpi.daysPerWeek, done: days >= kpi.daysPerWeek };
}
```

**過去の記録がそのまま進捗になる。** KPIを今日決めても、今週すでに読書していれば
その日数が最初から入っている。「決めた瞬間に0からやり直し」にはしない。

- [x] KPIを選択だけで設定できる（3タップ以内）／「自分で決める」で数値入力もできる
- [x] 進捗が「今週 2 / 3日」の形で出る。**過去の記録が最初から反映されている**
- [x] 週の区切りが週次レビューと一致している（月曜起点）

## 3. M-2：クエストを「具体化」する

### 3.1 やること

クエストを**増やさない**。既存の `complete_session` の**文言だけ**を使命に向けて書き換える。

```text
【使命なし／今週すでに達成】  1セッションを終える              +10 XP
【使命あり・今週まだ未達】    読書で1セッションを終える ⚔使命  +10 XP
                                   ↑ ここだけが変わる
```

- **達成判定は一切変えない。** どのジャンルで集中しても、今までどおりこのクエストは達成になる
- 変わるのは `label` と、⚔使命バッジの有無だけ
- **今週すでに達成している日は、通常の文言に戻す**（押しつけない）

### 3.2 なぜ4件目を足さないのか（数字で）

```text
いま：25分の集中 = 25 XP
      ＋「5分だけ始める」      +5 XP   ← 同じ集中で自動的に達成
      ＋「1セッションを終える」+10 XP  ← 同じ集中で自動的に達成
      合計 40 XP

4件目（+15XP）を足すと：
      同じ25分の集中で 55 XP（＋37%）
      努力は増えていないのに、報酬だけ増える
```

これは**フェーズ3でわざわざ是正した問題の再発**であり、
GQの基準「**努力を要求しない報酬は与えない**」に正面から反する。

副作用も2つある。
- 「3/3 達成」の気持ちよさが「3/4」になる日が増える
- 使命を設定した人だけ4件になり、件数が人によって不揃いになる

**具体化なら、XPも件数も達成率も一切動かない。** それでいて「今日やること」は具体的になる。

### 3.3 別のジャンルで集中した日

**クエストは達成する。使命の進捗は進まない。**

```text
月  📚 読書 25分   → 使命 1/3 ✓   クエスト達成 ✓
火  🗣️ 英語 25分   → 使命 1/3     クエスト達成 ✓   ← 集中したことは必ず認める
水  📚 読書 25分   → 使命 2/3 ✓   クエスト達成 ✓
```

ここでクエストまで未達にすると「**使命以外の勉強は無駄**」というメッセージになる。
GQは成長支援ツールであって、使命の管理ツールではない。

### 3.4 実装上の注意（2026-08-05 追記。M-1 のあと調べて分かったこと）

**① 使命が2つ以上ある場合、どれを使うか**

`build` を**上から順に見て、最初の「KPIあり かつ 今週まだ未達」のもの**を使う。
全部達成済み、または KPI が1つも無ければ、通常の文言に戻す。

複雑な優先順位（残り日数が少ない順など）は作らない。**上から順が一番説明しやすい。**

**② 読み込み順の罠（掟2）— ここが今回の急所**

```text
読み込み順: areas → core → progression → quests → timer → … → boot → otomon
                                          ↑ 4番目            ↑ 9番目
  quests.js は 120行目で renderDailyQuests() を呼んでいる（読み込み時に1回描画する）
  使命のデータ（mission）は boot.js の中。この時点ではまだ存在しない
```

**quests.js の初回描画では、使命はまだ読めない。** 対応は2つとも必要。

```javascript
// quests.js 側：裸の識別子で呼ばない。boot.js 未読込でも落ちない形にする
const label = (window.missionQuestLabel && window.missionQuestLabel(q.id)) || q.label;
```

```javascript
// boot.js 側：使命が読めるようになった後で、もう一度描き直す
//   ① boot.js の初期化の最後（mission を読み終えたところ）で 1回
//   ② KPIを保存・変更・削除したとき（saveMission() の後）
if (typeof renderDailyQuests === 'function') renderDailyQuests();
```

> ⚠️ **`missionQuestLabel(...)` と裸で書かないこと。** quests.js の読み込み時点では
> boot.js が動いていないので ReferenceError になり、**そのファイルの残り全体が死ぬ**。
> 過去2回の起動フリーズと同じ形（architecture_review §4 の急所2）。

**③ `DAILY_QUESTS` の中身は書き換えない**

`DAILY_QUESTS` は定義そのもの。ここの `label` を上書きすると、
使命を消したときに元に戻らなくなる。**表示するときにだけ差し替える。**

- [x] **XPも件数も達成判定も変わっていない**（別ジャンルで集中してもクエストは達成する）
- [x] 今週すでに達成している日は、通常の文言に戻る

- [x] **リロード直後の初回描画で落ちない**（quests.js は boot.js より先に読まれる）

## 4. M-3：妖精のひとこと

### 4.1 大原則（ヨージの言葉）

> 妖精はどんな時も味方だから、いつでも優しく応援して

**責める言葉は1つも作らない。** これは飾りではなく仕様である。
フェーズ2で「連続0日」「1日目」という**喪失の通知でユーザーを迎えていた問題**を直したばかりで、
**KPIと進捗バーは同じ罠を持っている**。「今週 1/3」は、見ようによっては「2回サボった」と読める。

**数字だけを裸で出さない。必ず言葉を添える。**

### 4.2 5つの状態すべてに言葉を用意する

| 状態 | 妖精のひとこと |
|---|---|
| まだ余裕がある | 今週あと2日。今日やっておくと、後がラクだよ |
| あと1日で達成 | あと1日で達成。25分がしんどければ、10分でも1日に数えます |
| **今週は達成済み** | 今週の使命は達成。**今日は好きなことをする日でもいいよ** |
| **2週続けて未達** | 難しい週もあるよ。**週2日に減らしてみる？**（→ KPI変更へ導線） |
| 別のジャンルをやった日 | 今日は英語だったね。それも立派な一歩。読書は今週あと2日だよ |

### 4.3 特に大事な2つ

**達成した日は、もう押さない。** 「達成したので次はもっと」は成長支援ではなく要求。

**続かないときは、ハードルを下げる提案をする。** 2週続けて未達なら、
妖精から「週2日に減らす？」と提案し、その場でKPIを変えられるようにする。
**下げることは失敗ではない**、という態度をアプリ側が示す。

> ⚠️ 「がんばろう」「あと少し」だけの空虚な励ましにしないこと。
> **必ず具体的な逃げ道**（時間を短くしていい／回数を減らしていい／今日は休んでいい）を添える。

### 4.5 実装上の注意（2026-08-05 追記。M-2 のあと調べて分かったこと）

**① どこに出すか — 使命カードの中。既存のナッジ枠には出さない**

```text
⚔ ヨージの使命
  🌱 育てたい習慣
    ○ 読書を続ける
        今週 2 / 3日   📚 読書・1日25分   [変更]
        🧚 あと1日で達成。25分がしんどければ…   ← ここに出す（KPI進捗のすぐ下）
```

**`#nudge-body`（今日のクエストカードの中）には出さないこと。**
あそこは既にナッジコースが使っている枠で、**同じ場所を2つの機能が奪い合うと
表示が消し合う**。ギルドPhase4で実際に起きた事故（NPCひとことと💪自信トーストが
同じ枠を取り合った）と同じ形になる。

**トーストにもしない。** 使命の話は「今そこにある情報」であって、
割り込んで伝えるものではない。

**② どの使命について喋るか**

M-2 と同じ規則。**`build` を上から順に見て、最初の「KPIあり かつ 今週まだ未達」**。
KPIのある使命が全部達成済みなら、**その最初の1つ**について達成済みの言葉を出す。

ただし**言葉は使命ごとに出す**（KPIを持つ使命それぞれの進捗の下に、その使命の言葉）。
「どれについて喋るか」を悩まなくて済むし、2つ目の使命が無視されない。

**③ 「2週続けて未達」をどう判定するか**

いまの `missionWeekProgress(kpi)` は今週しか見られない（`getWeekKey(new Date())` 固定）。
**週を渡せるようにする。**

```javascript
// 変更前: function missionWeekProgress(kpi)
// 変更後: 第2引数で週を指定できるようにする（省略時は今週＝既存の呼び出しはそのまま動く）
function missionWeekProgress(kpi, weekKey = getWeekKey(new Date())) { … }

// 先週
const lastWeek = getWeekKey(new Date(Date.now() - 7 * 864e5));
```

「2週続けて未達」＝ **先週が未達 かつ 今週も残り日数では届かない**。
今週まだ間に合うなら、その言葉は出さない（早すぎる諦めを勧めない）。

**④ 「別のジャンルをやった日」をどう判定するか**

```javascript
// 今日の記録を見る。使命のジャンルは基準未満、でも他のジャンルでは集中している
const today = data.historyDetails?.[dkey(new Date())]?.genres || {};
const missionMins = today[kpi.genreId] || 0;
const otherMins   = Object.entries(today)
  .filter(([g]) => g !== kpi.genreId)
  .reduce((s, [, m]) => s + m, 0);
const didOtherGenre = missionMins < kpi.minsPerDay && otherMins > 0;
```

**⑤ KPIを下げる導線は、既存の編集画面を再利用する**

「週2日に減らしてみる？」のボタンは、**既にある `data-mc-kpi-open` を押すのと同じ**にする。
新しいUIを作らない。押すとKPI編集が開き、そこで日数を選び直せる。

### 4.4 M-3 の受け入れ基準

- [ ] 5つの状態それぞれで、対応する言葉が出る
- [ ] **責める語（サボった・遅れています・未達成のまま 等）が1つも無い**
- [ ] 達成済みの日は、追加の行動を促さない
- [ ] 2週続けて未達のとき、KPIを下げる導線がその場から使える
- [ ] 数字だけが単独で出ている箇所が無い（必ず言葉が添えられている）
- [ ] **使命カードの中に出ている**（`#nudge-body` を使っていない・トーストにしていない）
- [ ] **KPIを持つ使命それぞれに、その使命の言葉が出る**
- [ ] **今週まだ間に合ううちは「減らしてみる？」を出さない**
- [ ] KPIを下げる導線が、既存のKPI編集（`data-mc-kpi-open`）の再利用になっている
- [ ] `missionWeekProgress(kpi)` の既存の呼び出しが、引数追加後もそのまま動く
- [ ] コンソールエラーゼロ／`bump_version.sh` 実行済み

## 5. テスト手順

1. `python3 -m http.server 8123` を立て `http://localhost:8123/index.html` を開く
   （`preview_start` のサーバーはサンドボックス制約で全404）
2. **既存データが壊れないこと**（最重要）
   ```javascript
   // kpi の無い、今までの形の使命を入れて開く
   localStorage.setItem('gq_mission', JSON.stringify({
     build: [{ text: '読書を続ける', done: false }], quit: [] }));
   ```
   → 表示・チェックが今までどおり動き、「どうなれば達成か決める」が出ること
3. **進捗の数え方**
   ```javascript
   // 今週の月曜と水曜に読書30分ずつの記録を作る（genreId は実際の値に合わせる）
   var d = JSON.parse(localStorage.getItem('gq_data'));
   d.historyDetails['2026-08-03'] = { sessions:1, genres:{ g_reading:30 } };
   d.historyDetails['2026-08-05'] = { sessions:1, genres:{ g_reading:30 } };
   localStorage.setItem('gq_data', JSON.stringify(d));
   ```
   → KPI（週3日×25分）を設定した直後に「今週 2 / 3日」と出ること
   → `minsPerDay` を 50 にすると「0 / 3日」になること（30分では1日と数えない）
4. **週の区切り**: 日曜と月曜をまたいで、週次レビューの「今週」と一致すること
5. **クエストの具体化**: 使命ありで文言が変わる／達成済みで戻る／XPが変わらない
6. **妖精の5状態**: 進捗を作り分けて、5つの言葉がすべて出ること
7. **新規ユーザー**: `localStorage.clear()` → リロードで起動し、使命が空でも壊れないこと
8. コンソールエラーがゼロであること
9. `bash tools/bump_version.sh` → push後 `curl -s https://yoz400.github.io/growth-quest/ | grep v=guild-`

## 6. 迷ったら止まって報告すること

- 週の区切りが、週次レビューの実装とどうしても一致しない
- `historyDetails` にジャンル別の記録が無い日が多く、進捗がほとんど0になる
