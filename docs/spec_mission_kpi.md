## 1. 何を解決するか

**使命と、日々のクエストが繋がっていない。**

```text
【いま】
  ⚔ 使命        「読書を続ける」        毎日チェックを押すだけ
                                        ↑ 押しても何も起きない。ただのメモ
  📋 クエスト    5分だけ始める
                 1セッションを終える     ← 全員同じ固定3件
                 今日の自分をほめる

  この2つは、コードの上でも完全に別々（quests.js と boot.js で無関係）
```

使命は「決めた」だけで終わっていて、**今日なにをすれば近づくのかが分からない**。
クエストは全員同じで、**その人が何を目指しているかを知らない**。

この仕様は2つを1本の線にする。

```text
【あと】
  使命「読書を続ける」
    ↓ どうなれば達成か（KPI）
  週3日 × 25分
    ↓ 今週の残りから逆算
  今日の一手「読書で25分」
    ↓ クエストの文言に反映
  📋 読書で1セッションを終える  ⚔使命
    ↓ どの状態でも
  🧚 妖精が優しく声をかける
```

### やらないこと（スコープ境界）
- **「断ちたい習慣」は対象外**。あれは「やらなかった日数」で測るもので、
  回数×時間では測れない。仕組みが別なので、まとめて作らない
- **クエストを増やさない**（§4 で理由を数字とともに示す）
- **新しい localStorage キーを増やさない**（`gq_mission` の中に収める。掟4の手続きが不要になる）

## 2. M-1：使命にKPIを持たせる

### 2.1 データ構造（既存データを壊さない）

いまの `gq_mission` は `{ build: [{text, done}], quit: [...] }`（[boot.js:1547](../scripts/boot.js:1547)）。
**`build` の各要素に `kpi` を足すだけ**にする。

```javascript
{
  text: '読書を続ける',
  done: false,            // 既存。その日のチェック（毎日リセット）。触らない
  kpi: {                  // 追加。無い＝未設定。既存データはこのまま動く
    genreId:     'g_reading',  // どのジャンルの集中を数えるか
    daysPerWeek: 3,            // 週に何日やれば達成か
    minsPerDay:  25,           // 1日あたり何分で「1日」と数えるか
  }
}
```

> ⚠️ **`kpi` が無い既存の使命を壊さないこと。** 未設定として扱い、
> カードに「どうなれば達成か決める」ボタンを出すだけにする。
> **勝手に既定値を入れない**（ヨージが決めていない目標を押しつけることになる）。

### 2.2 なぜ「週3回」ではなく「週3日」なのか

**既存データで数えられるのが日数だから。**

```text
data.historyDetails['2026-08-05'] = {
  sessions: 3,                    ← 1日の合計回数。ジャンル別ではない
  genres: { g_reading: 50, ... }  ← ジャンル別は「分」しか持っていない
}
```

ジャンル別のセッション回数は記録されていない。**「読書で3回」は今のデータでは数えられない。**
記録形式を変えると既存ユーザーの履歴に手を入れることになるので、やらない。

代わりに「**その日、読書を `minsPerDay` 分以上やったか**」で1日と数える。
習慣の目標としても「週3日読書する」のほうが自然で、
「1回を短く刻んで3回にする」という抜け道も生まれない。

### 2.3 KPIの決め方（選択式＋自由記入）

**選ぶだけで決まるのが既定。自由記入も選べる。**
ここで入力に手間がかかると、使命が空のまま放置される。

```text
📚 どのジャンル？    [📖 学習] [🗣️ 英語] [📚 読書] …  ← 既存ジャンルから選ぶ
🗓 週に何日？        [1日] [2日] [3日] [5日] [毎日] [自分で決める]
⏱ 1日どれくらい？   [10分] [25分] [50分] [自分で決める]
```

- 「自分で決める」を押したときだけ数値入力を出す
- 既定の選択は **週3日 × 25分**（ポモドーロ1回ぶん）
- ジャンルが1つしかない人は、ジャンル選択を出さずにそれを使う

### 2.4 進捗の数え方

**週は月曜起点。** 週次レビューと同じ区切りを使う
（[calendar-review.js:676](../scripts/calendar-review.js:676) `dowIndex` が Mon=0 とする定義。
[1237行](../scripts/calendar-review.js:1237) の `_weekGenreMins` も月曜から7日ぶん数えている）。

> ⚠️ **週の区切りを自分で定義しないこと。** ここで日曜起点にすると、
> 週次レビューと使命で「今週」がズレる。GQ最頻出のバグ（データと画面のズレ）と同型。

```javascript
// 今週、KPIを満たした日が何日あるか
function missionWeekProgress(kpi) {
  const mon = mondayOfThisWeek();           // 既存の週の求め方に合わせる
  let days = 0;
  for (let i = 0; i < 7; i++) {
    const d = new Date(mon); d.setDate(mon.getDate() + i);
    const mins = data.historyDetails?.[dateKey(d)]?.genres?.[kpi.genreId] || 0;
    if (mins >= kpi.minsPerDay) days++;
  }
  return { days, target: kpi.daysPerWeek, done: days >= kpi.daysPerWeek };
}
```

**過去の記録がそのまま進捗になる。** KPIを今日決めても、今週すでに読書していれば
その日数が最初から入っている。「決めた瞬間に0からやり直し」にはしない。

### 2.5 M-1 の受け入れ基準

- [x] `kpi` の無い既存の使命が、今までどおり表示・チェックできる（壊れない）
- [x] KPIを選択だけで設定できる（3タップ以内）／「自分で決める」で数値入力もできる
- [x] 進捗が「今週 2 / 3日」の形で出る。**過去の記録が最初から反映されている**
- [x] 週の区切りが週次レビューと一致している（月曜起点）
- [x] `localStorage` のキーが増えていない（`gq_mission` の中だけ）
- [x] `exportAllData()` で KPI ごとバックアップされる（`gq_mission` に入っているので自動）
- [x] コンソールエラーゼロ／`bash tools/bump_version.sh` 実行済み

## 3. M-2：クエストを「具体化」する

### 3.1 やること

クエストを**増やさない**。既存の `complete_session` の**文言だけ**を使命に向けて書き換える。

```text
【使命なし／今週すでに達成】  1セッションを終える              +10 XP
【使命あり・今週まだ未達】    読書で1セッションを終える ⚔使命  +10 XP
                                   ↑ ここだけが変わる
```

- **達成判定は一切変えない。** どのジャンルで集中しても、今までどおりこのクエストは達成になる
- 変わるのは `label` と、⚔使命バッジの有無だけ
- **今週すでに達成している日は、通常の文言に戻す**（押しつけない）

### 3.2 なぜ4件目を足さないのか（数字で）

```text
いま：25分の集中 = 25 XP
      ＋「5分だけ始める」      +5 XP   ← 同じ集中で自動的に達成
      ＋「1セッションを終える」+10 XP  ← 同じ集中で自動的に達成
      合計 40 XP

4件目（+15XP）を足すと：
      同じ25分の集中で 55 XP（＋37%）
      努力は増えていないのに、報酬だけ増える
```

これは**フェーズ3でわざわざ是正した問題の再発**であり、
GQの基準「**努力を要求しない報酬は与えない**」に正面から反する。

副作用も2つある。
- 「3/3 達成」の気持ちよさが「3/4」になる日が増える
- 使命を設定した人だけ4件になり、件数が人によって不揃いになる

**具体化なら、XPも件数も達成率も一切動かない。** それでいて「今日やること」は具体的になる。

### 3.3 別のジャンルで集中した日

**クエストは達成する。使命の進捗は進まない。**

```text
月  📚 読書 25分   → 使命 1/3 ✓   クエスト達成 ✓
火  🗣️ 英語 25分   → 使命 1/3     クエスト達成 ✓   ← 集中したことは必ず認める
水  📚 読書 25分   → 使命 2/3 ✓   クエスト達成 ✓
```

ここでクエストまで未達にすると「**使命以外の勉強は無駄**」というメッセージになる。
GQは成長支援ツールであって、使命の管理ツールではない。

### 3.4 M-2 の受け入れ基準

- [ ] 使命KPIがあり今週未達のとき、クエストの文言が「〈ジャンル名〉で1セッションを終える」になる
- [ ] ⚔使命バッジが付く
- [ ] **XPも件数も達成判定も変わっていない**（別ジャンルで集中してもクエストは達成する）
- [ ] 今週すでに達成している日は、通常の文言に戻る
- [ ] 使命KPIが無い人の画面は、今までと1文字も変わらない
- [ ] コンソールエラーゼロ／`bump_version.sh` 実行済み

## 4. M-3：妖精のひとこと

### 4.1 大原則（ヨージの言葉）

> 妖精はどんな時も味方だから、いつでも優しく応援して

**責める言葉は1つも作らない。** これは飾りではなく仕様である。
フェーズ2で「連続0日」「1日目」という**喪失の通知でユーザーを迎えていた問題**を直したばかりで、
**KPIと進捗バーは同じ罠を持っている**。「今週 1/3」は、見ようによっては「2回サボった」と読める。

**数字だけを裸で出さない。必ず言葉を添える。**

### 4.2 5つの状態すべてに言葉を用意する

| 状態 | 妖精のひとこと |
|---|---|
| まだ余裕がある | 今週あと2日。今日やっておくと、後がラクだよ |
| あと1日で達成 | あと1日で達成。25分がしんどければ、10分でも1日に数えます |
| **今週は達成済み** | 今週の使命は達成。**今日は好きなことをする日でもいいよ** |
| **2週続けて未達** | 難しい週もあるよ。**週2日に減らしてみる？**（→ KPI変更へ導線） |
| 別のジャンルをやった日 | 今日は英語だったね。それも立派な一歩。読書は今週あと2日だよ |

### 4.3 特に大事な2つ

**達成した日は、もう押さない。** 「達成したので次はもっと」は成長支援ではなく要求。

**続かないときは、ハードルを下げる提案をする。** 2週続けて未達なら、
妖精から「週2日に減らす？」と提案し、その場でKPIを変えられるようにする。
**下げることは失敗ではない**、という態度をアプリ側が示す。

> ⚠️ 「がんばろう」「あと少し」だけの空虚な励ましにしないこと。
> **必ず具体的な逃げ道**（時間を短くしていい／回数を減らしていい／今日は休んでいい）を添える。

### 4.4 M-3 の受け入れ基準

- [ ] 5つの状態それぞれで、対応する言葉が出る
- [ ] **責める語（サボった・遅れています・未達成のまま 等）が1つも無い**
- [ ] 達成済みの日は、追加の行動を促さない
- [ ] 2週続けて未達のとき、KPIを下げる導線がその場から使える
- [ ] 数字だけが単独で出ている箇所が無い（必ず言葉が添えられている）
- [ ] コンソールエラーゼロ／`bump_version.sh` 実行済み

7. **新規ユーザー**: `localStorage.clear()` → リロードで起動し、使命が空でも壊れないこと

**Codexが仕様書より良くした点**

- **週の計算を自前で書かず、週次レビューの `getWeekKey` / `getWeekDates` をそのまま呼んだ。**
  仕様書は「calendar-review.js の求め方に合わせること」としか書いていなかったが、
  同じ関数を通すのが最も安全で、「今週」がズレる余地が構造的に無くなった
- **不正値のバリデーションを足した**（1〜7日／1〜1440分）。仕様書には書いていなかった
- 保存前に `validMissionKpi()` で形を検証してから使っている。壊れたデータが入っても落ちない

**指摘（実害なしだが記録に残す）**

仕様書に無い変更として、**使命項目の識別を `id` から配列の番号に変えた**
（`data-mc-toggle="build:0"` の形）。

```javascript
// 変更前                                    // 変更後
const it = arr.find(x => x.id === id);       const it = arr[Number(index)];
mission[kind] = arr.filter(x => x.id !== id); mission[kind].splice(Number(index), 1);
```

- **使命項目には元から `id` がある**（`mb...` / `mq...`。[boot.js:2086](../scripts/boot.js:2086) で採番）。
  KPIの編集に添字が要ったとしても、`id` のままでも書けた
- 実機で「2つある使命のうち1つ目を削除しても、2つ目のKPIが正しく残る」ことは確認済み。
  レンダリングの直後にしかクリックが来ない構造なので、現状は安全
- ただし `|| []` の防御が消えている（`mission[kind]` が配列である保証を
  `loadMission()` に全面的に依存する形になった）

**今は動いているので戻さない**が、将来この配列を非同期に触る処理が入ると
取り違えの余地ができる。次に使命まわりを触るときに `id` 方式へ戻すのが望ましい。

> 💡 **学び**: 「実装の都合で識別子を変える」は、仕様書に書かれていなくても
> データの意味に関わる変更になる。**受け入れ基準を満たしていても、
> 仕様外の変更は差分レビューでしか見つからない。** コミットの diff は必ず全部読む。
