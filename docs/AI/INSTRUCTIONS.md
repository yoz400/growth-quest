# INSTRUCTIONS — テンプレート集

依頼・報告・記録の標準形式。

---

## 1. 実装を誰に振るか（損益分岐点）

仕様書を書いて Codex に渡すのは固定費がかかる。実装が小さいほど赤字になる。

| 変更規模 | 担当 |
|---|---|
| 1ファイル・50行以下 | **クロがその場で直す**（仕様書を書かない） |
| 1〜2ファイル・50〜150行 | 既にコンテキストが載っていればクロ、なければ Codex |
| 複数ファイル / 150行超 / 新機能 | **仕様書を書いて Codex へ** |
| 同種の作業の繰り返し | **必ず Codex**（仕様書1本を複数回使える） |

---

## 2. ChatGPT に回す仕事

コードを1バイトも必要としない仕事は、すべて ChatGPT へ。
クロで始めると開始時点で1〜3万トークンが乗るため、同じ成果物なら純粋な損。

- ゲームデザイン・世界観・報酬設計
- 優先順位・ロードマップ
- 文言・コピー・UXライティング
- **仕様書の目的妥当性チェック**（仕様書を貼るだけ。層3の独立検証を兼ねる）
- ユーザー価値の検討

### 大きめの機能を作る前に必ず通すこと

クロが仕様書を書いた後・Codexが実装を始める前に、ChatGPT へ仕様書を貼って
**「この仕様は目的に合っているか」を1回だけ確認する。**

理由: クロが仕様も書きレビューもするため、「仕様書自体が間違っている」ケースを
誰も検出できない。Codexが仕様どおり実装しても、仕様が間違っていれば結果も間違う。

---

## 3. クロへの依頼テンプレート

```md
## Task
（1行）

## Why
（何に貢献するか）

## 受け入れ基準（これが全て真なら完了）
- [ ]
- [ ]

## 触ってよい範囲

## 触ってはいけない範囲

## 参照すべき文書
docs/AI/CURRENT.md, docs/spec_xxx.md
```

**受け入れ基準は作業前に書く。** 後から書いた基準は検証として機能しない。

### 受け入れ基準の書き方

| ✗ 悪い | ○ 良い |
|---|---|
| 表示を速くする | 起動から初回描画まで1.5秒以内 |
| バグを直す | ナッジコース選択中に起動してもコンソールエラーが0件 |
| きれいにする | check_load_order.py がエラー0件で通る |
| 図鑑を改善する | 未取得のオトモンがシルエット表示になり、タップで入手条件が出る |

**「実行して真偽を確認できるか」**が判定基準。

---

## 4. Codex への依頼

`docs/spec_*.md` の末尾にある依頼文をコピペする。
仕様書には必ず「受け入れ基準」「テスト手順」「迷ったら止まって報告」を書く。

---

## 5. レビューのやり方（差分のみ）

```text
✗ 悪い: 仕様書 + 変更ファイル全体 + 周辺コード = 約70kトークン
○ 良い: git diff + 受け入れ基準だけ        = 約 4kトークン
```

**約17分の1。精度は落ちない**（無関係なコードが視界に入らないぶん判断が鋭くなる）。

読み込み順・依存関係の問題は差分では見えないので `check_load_order.py` に任せる。

---

## 6. 完了報告の形式

```md
## Completed     受け入れ基準ごとに、満たした根拠を1行
## Remaining     残作業（無ければ「なし」）
## Problems      発生した問題・想定外（無ければ「なし」）
## Decisions     作業中に判断したこと + DECISIONS.md 記録要否
## Next Action   次にやること 1〜3件
## Diff          git diff --stat の出力
```

### 完了チェックリスト

```md
- [ ] 受け入れ基準を全て満たした（各項目に根拠を1行）
- [ ] CSS/JS を編集したなら bump_version.sh を実行した
- [ ] JS を編集したなら check_load_order.py を実行した
- [ ] ブラウザで動作確認した（条件付き経路は条件を作って確認した）
- [ ] 依頼範囲外のファイルを変更していない
- [ ] CURRENT / DECISIONS / FAILURES の更新要否を判断した
```

## 7. ChatGPT 側のカスタム指示

ChatGPT のカスタム指示、または Growth Quest 用 Project の指示欄に設定する。

```text
あなたは THINK ロールです。企画・優先順位・文言・ゲームデザインが仕事です。
実装の細部は別のAI（クロ／Codex）が担当するので深入りしないでください。

ユーザーの名前はヨージ。説明はすべて初心者向けに、専門用語は必ず意味を説明。
重要な概念はテキスト図で視覚的に伝えてください。

【必須】結論・決定が出たら、回答の最後に必ず保存用ブロックを出力してください。

---SAVE---
保存先: docs/AI/DECISIONS.md
## YYYY-MM-DD
### Decision
### Why
### Alternatives
### Consequence
---END---

保存に値する結論が出ていない回答では、このブロックを出力しないでください。
実装方針に触れるときは「これはクロがコードを確認して確定すべき」と明示してください。
```


```md

```

## 9. 週次チェック（15分）

```md
- [ ] CURRENT.md が60行以内 / 更新日が3日以内か
- [ ] DECISIONS.md に今週の追記があるか（0件が続くなら記録経路が壊れている）
- [ ] レビューで実際に指摘が出たか（0件が続くなら検証が形骸化している）
- [ ] AIにレビューさせている項目で、スクリプト化できるものはないか
      （1つスクリプト化するたびに以後永久にコストが下がる）
- [ ] commit / push 済みか
```
