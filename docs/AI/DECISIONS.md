## 2026-10-24 — お供の挨拶を「画面下の絵文字」から「ヘッダー直下に本人が出る」へ

### Decision

ログイン時に出るお供オトモンの声（`#otomon-nudge`）を次のように変えた（guild-203）。

| | 前 | 後 |
|---|---|---|
| 位置 | 画面下 `bottom:22px`（はみ出していた） | **ヘッダー直下**（`topBelowHeader()` で実測） |
| 絵 | 絵文字1文字 `🧚` | **その子の画像**（`otomonFace(o,'medium')`・62px枠） |
| モーダル中 | そのまま出して裏に隠れていた | **閉じるまで待ってから出す**（最大90秒） |
| 表示時間 | 4.8秒 | 5.6秒（タップで即閉じ可） |

### Why

ヨージ報告「ログイン時のセリフをもっと目立つ場所に。オトモン自体も出現させて」。
調べたら、**そもそも見えていなかった**。

```
ナッジ z-index 90  <  ログインボーナス z-index 130
→ ログイン直後はモーダルの裏で出て、誰にも見られないまま4.8秒で消えていた
```

実測で、ナッジの座標の最前面は `#login-bonus-overlay` だった。
位置も `bottom:22px` で、画面高さ768に対し bottom 776 と**はみ出していた**。

### Alternatives

- **z-index を上げてモーダルより前に出す**: 祝福の最中に声が重なる（基準3）。却下。
  「待ってから出す」なら、ログインボーナスを見終わってから挨拶が届く
- **画面中央に大きく出す**: STARTボタンを覆う恐れ（基準2）。却下
- **週次レビューの帯と同じ高さに固定**: 同時に出ると重なる。帯が出ているときは下へずらす形にした

### Consequence

- 縦位置はCSSに書かず、出す瞬間に実測する（ヘッダー高は端末で変わる・2026-08-28の事故と同じ理由）
- **アニメ途中の座標を拾う罠**: レビューの帯は .45s かけて降りるため、その最中に
  `getBoundingClientRect()` を読むと画面外のマイナス値が返る。そのまま使うと挨拶が
  ヘッダーの上や画面外に出たので、`topBelowHeader()` を下限に固定した
- `showNudge(emoji, text, otomon)` の第3引数は任意。渡さない呼び出し
  （節目の報酬・連続ふれあいの祝福）は従来どおり絵文字で出る＝後方互換

## 2026-10-24 — ギルド依頼3件ごとに目覚めアイテムを渡す（蛇口を太くする）

### Decision

`completeGuildQuest()` で、累計達成が `GUILD_WAKE_EVERY`(=3) の倍数になった回に
目覚めアイテムを1つ渡す（guild-201）。確率ではなく**必ず**配る。

### Why

guild-198 で「配られても使えない」詰まりは抜けたが、**量はまだ釣り合っていなかった**。

```
一周(29セッション)あたり   もらう卵 4.3個 / 孵せる卵 1.39個
                           → 毎周 2.9個ずつ溜まり続ける
釣り合わせるのに足りない量 = 9.8個/周 ≒ 3セッションに1個
```

ヨージの当初の要望「入手方法を増やしたい」は数字の上でも正しかった。
ガチャ案も出たが、**努力の対価で手に入るほうがよい**とヨージ本人が結論。
ギルド依頼は既に22件あり、完全に努力の対価なので、ここに乗せるのが最小で最も効く。

### Alternatives

- **確率で配る（例: 2割で1個）**: 運に左右され「努力の対価」でなくなる。
  「あと1件で届く」も見えず目標にならない。却下
- **SUGOROKU_WAKE_RATE を上げる**: ばらまき。判断基準1に抵触しうる。却下
- **新しい保存キーで「配布済み」を管理**: 達成の瞬間にだけ判定すれば不要だった。
  起動のたびに数え直す設計にすると過去分を何度も配ってしまうので、**イベント時のみ**判定する

### Consequence

- **保存するものを増やしていない**。既存の `guild.completions` の合計が倍数か見るだけ
- `guild-198` と噛み合う：配るときは手持ちの卵が使える種類が優先される
  （検証：はっぱ／こもれびの卵を持った状態で `smile_bell`・`power_nut` が出た）
- 配る量の目安：依頼を1日3件こなす人で約1個/日。上の「3セッションに1個」とほぼ一致
- 多すぎた場合は `GUILD_WAKE_EVERY` を4〜5に上げるだけで調整できる
- 検証：3・6・9件目ちょうどで配布、それ以外の回は配られないことを実機UI経由で確認

## 2026-10-24 — 毎日ログイン型カレンダーUIは真似しない（既にGQの方が良い）

### Decision

ヨージが「優秀」と評価した他社UI（LINEマンガの毎日ガチャチケット：31日グリッドに
「獲得／未獲得」を並べる形）を **GQには持ち込まない**。
代わりに、既存の月カレンダーに**分母だけ**足した（guild-200）。

```
この月の学習日数: 18日  →  この月の学習日数: 18日 / 24日経過
```

### Why

実物を並べて比べたところ、**GQの既存カレンダーの方が優れていた**。

| 他社UI | GQ（既存） |
|---|---|
| 獲得／未獲得の2値 | ● ★ 🌸 ✨ の4段階＋分数 |
| 落とした日が灰色で残る＝責める | 落とした日は**ただの空白**＝責めない |
| 連続が読めない | 日と日が点でつながる（`streak-right`） |
| 月の要約なし | 学習日数・学習時間・ベストの日（`cal-stats`） |

他社UIの目的は「毎日アプリを開かせる」（ガチャ→課金への導線）。
GQの目的は「気がついたら楽しみながら成長していた」で、**目的が違う**。
開くだけで報酬が出る設計は判断基準1に反し、GQは既にログインボーナスを
420XP→20XPに下げて逆方向へ舵を切っている。ここで同じ思想を入れると自分で巻き戻すことになる。

空白を「埋めたくなる」演出は、裏返すと**毎回「落とした日」を突きつける**ことであり、
判断基準4「サボった人を迎えるか、責めるか」に反する。

### Alternatives

- **月の草ヒートマップを新設**: 調べたら `buildStreakHeatmapSVG`（26週分）と
  ホームの月カレンダーが既にあり、重複になる。却下
- **達成率バー／「あと○日」**: 埋まっていない所を強調＝責める作り。却下
- **何もしない**: 分母が無いと「18日」が多いのか少ないのか読めない。1点だけ採用した

### Consequence

- 変更は `renderCalStats()` の1か所・実質3行。未来の月は分母を出さない（経過0日のため）
- 「他社UIが優秀に見えるとき、目的が同じかを先に問う」が判断の型として残った

## 2026-10-24 — 特別卵の目覚めアイテムは「節目の達成」でだけ配る

### Decision

特別卵（SSR）が受け付ける 🔖自信のしおり / 🌈にじいろの雫 は、
**随時ドロップには入れず、積み上げの節目にだけ配る**（guild-199）。

| 達成 | 既存バッジ | 配るもの | 累計 |
|---|---|---|---|
| 世界樹に実を10個 | `sk_10` | 自信のしおり ×2 | 2 |
| 30日つづけた | `st_30` | にじいろの雫 ×2 | 4 |
| 100日つづけた | `st_100` | にじいろの雫 ×1 | **5** |

合計5個＝`HATCH_GOAL.SSR` ちょうど。**3つ達成した人だけが特別卵を1体孵せる**。

### Why

特別卵は accepts がこの2つだけで、どちらも `special` 付きのため
`grantRandomWakeItem()` の対象外＝**通常プレイでは永久に孵せなかった**（2026-10-23 発見）。
`special` は「ばらまかない」という意思表示なので、ランダム配布に加えるのではなく
**努力の節目という入手経路を与える**（判断基準1：努力を要求しない報酬を与えない）。

ヨージの原案は「11個 / 100日連続ログイン / 21日連続」。2点だけ修正した。

- **ログイン連続は廃止済み**（boot.js のコメント参照。学習連続 `data.streak` に一本化）。
  そもそも「開くだけ」は努力を要求しないので、基準1の観点でも学習連続が正しい
- **数字は既存の節目に合わせた**（11→10、21→30）。新バッジを足さずに済む。
  21日に最も近い「習慣化できた」節目として30日を採用

### Alternatives

- **special をドロップに加える**: ばらまきになり、特別卵の特別さが消える。却下
- **累計100日（`d_100`）にする**: 休んでも積み上がるので基準4に優しいが、
  ヨージが「連続」を選択。達成感を優先
- **バッジ側（settings-genre.js）で配る**: `checkBadges()` は boot.js の読み込み時にも
  走り、その時点で otomon.js は未読込＝静かに配り損ねる（掟2）。却下
- **セッション直後に知らせる**: 祝福が渋滞する（基準3）。次に開いたときに知らせる形にした

### Consequence

- 新キー **`gq_milestone_rewards`**（配布済みフラグ）。`gq_` 接頭辞なので
  `isBackupKey` によりバックアップ対象に自動で入る。台帳 §6 に追記済み
- **すでに達成済みの人にも遡って1回だけ配る**。バッジは再発火しないため、
  「バッジを取った瞬間」ではなく「まだ配っていない達成」を起動時に見て配る
- 配布の判定は otomon.js（最後に読まれる）が `gq_badges` を直読みする。
  ファイル間参照を作らないので読み込み順の事故が構造的に起きない
- 検証: 3つ達成で合計5個 → 特別卵に5回使って孵化し `niji_slime` が仲間になることを確認

## 2026-10-23 — 孵化アイテムは「手持ちの卵が使える種類」を優先して配る

### Decision

`grantRandomWakeItem()` が14種から完全ランダムに配っていたのを、
**いま持っている卵の `accepts` の和集合を優先**するよう変更（guild-198）。
使える種類が1つも無いとき（卵ゼロなど）は従来どおり全体から配る。

### Why

ヨージ報告「卵ばかり溜まって孵化アイテムが全然手に入らない。萎える原因になりかねない」。
配る側が手持ちの卵を一切見ていなかった。実測（20万回）:

- 卵1個のとき、出たアイテムが使える確率は **18%**（82%が無駄）
- クエストは1つずつなので実質は1個の卵に対する確率。はっぱ/こだま **14.3%**、
  まよけ/ねむりは受け付けが1種しかなく **7.1%**（平均14回に1回）
- 卵1個を孵すまで: ふつうの卵 **5.0周=146セッション**／最悪 **10.1周=292セッション**
- B適用後はどちらも **0.7周=21セッション**

孵る側（`candidatePoolIds`）には既に「未所持を優先」が入っていた。
**配る側に同じ配慮を入れ忘れていただけ**で、片側だけ直っている状態だった。

### Alternatives

- **出現率を上げる（SUGOROKU_WAKE_RATE 0.5→0.7）**: もらえる個数が増えるため
  判断基準1「努力を要求しない報酬を与えない」に抵触しうる。却下
- **卵の accepts を増やす**: 卵ごとの個性が消える。却下
- **7割だけ優先し3割はランダム**: 偏り対策になるが、まず全優先で実機を見てから判断

### Consequence

- **もらえる個数は変わらない**。無駄が減るだけなので基準1に触れない（ここがDとの違い）
- 手持ちが偏った卵1種だけだと、同じアイテムばかり出る。気になるなら上記の7:3案へ
- 保存データ（卵・アイテム在庫）には一切触れていない
- **未解決**: にじいろの卵(SSR)は accepts が `confidence_bookmark`/`rainbow_drop` の
  2つだけで、どちらも `special` 付きのため配布プールから除外されている
  → **通常プレイでは永久に孵せない**。はじまりの種（初期3個）を使い切ると詰む。別途対応が要る

## 2026-10-18 — 週次レビューの案内は「帯」で金色にする

### Decision

ヘッダー直下に浮いていた箱を、**#app の中身と同じ幅の帯**に変えた（`width: calc(100% - 32px); max-width: 448px`）。
色はシアン系から**金（--gold）**へ。見出し・枠・「開く」ボタンを金で揃える。

縦位置は従来どおり CSS に書かず、出す瞬間に `topBelowHeader()` で測って `style.top` に入れる。

### Why

- 幅250px固定が狭く「週次レビュータイ／ム！」と**語の途中で改行が割れていた**
- 箱が下のカードの上に中途半端に浮き、**学習ジャンルのボタンを隠していた**
- 地が濃紺（#13132b）で、ほぼ黒の背景に**沈んで見えた**。週の区切り＝節目なので、
  GQで節目に使っている金に寄せた（ヨージ決定）

### Alternatives

- **画面の下に出す**: 親指は届くが「新しい版のお知らせ」帯と場所が競合する。却下
- **位置はそのまま幅だけ広げる**: 変更は最小だがカードを覆う問題が残る。却下
- **紫〜藍のグラデ**: 落ち着くが、GQの他の画面で紫を使っておらずここだけ浮く。却下
- **シアンのまま濃くする**: 「お知らせ色」として一貫するが、ヨージは金を選択

### Consequence

- 幅は `#app` の padding に依存する。**`#app { padding }` を変えたら帯の
  `calc(100% - 32px)` と、`@media (max-width:360px)` の `calc(100% - 20px)` も直すこと**
  （CSSにコメントで明記済み）
- ✕ボタンは 20×16px のままで小さい。今回の依頼の範囲外なので触っていない

## 2026-08-24 — 完璧な週の相棒は「週に1体」。誰が来るかは週の日付から決める

### Decision

完璧な週を走るオトモンは、その週につき1体だけ。手持ちの中から
**その週の日付をもとに決める**（`pickRunnerForWeek`）。同じ週はいつ見ても同じ子、
週が変われば別の子。タップするとその子の図鑑の詳細が開く（`Otomon.openPanelAt`）。

### Why

最大4体を全部の週に出したところ、ヨージから「1つの週に手持ち全員出てしまう／
各週まったく同じ顔ぶれ」と指摘。賑やかすぎるうえ、週ごとの特別感が消えていた。
1体に絞ると「今週は誰が来たか」を見る楽しみが生まれ、タップの的も狙いやすくなる。

### Alternatives

- **毎回 Math.random() で選ぶ** … 却下。カレンダーは月送り・予定の追加・
  タイマー完了など、いろいろな場面で描き直される。そのたびに顔ぶれが
  入れ替わってチカチカし、「今週の子」という感覚が育たない
- **常にお供の子を出す** … 却下。ヨージの要望（週ごとに違う子）に反する。
  図鑑の子と再会する機会も失われる
- **タップで直接ふれあう** … 却下。ふれあいは「お供の子」だけの行為
  （`touchActiveOtomon` は active に働く）。詳細を開いて、お供なら「ふれあう」、
  そうでなければ「お供にする」を選べる今の形のほうが、仕組みと一致する

### Consequence

- `getRunnerPool()` の**並び順は必ず安定させる**（出会った順→id）。
  順番が揺れると「同じ週なのに別の子」になり、決め打ちの意味が消える
- 走るオトモンは `pointer-events: auto`＝その位置の日付マスは押せなくなる。
  当たり判定は36px（画像は22pxのまま余白で拡張）。1週1体にしたので影響は小さい

## 2026-08-23 — 新しい版は「勝手に読み直さず、帯を出して押してもらう」

### Decision

`version.json`（bump_version.sh が index.html と同時に書き出す）をアプリ再開時に
見に行き、番号が違えば画面下に「新しい版があります」の帯を出す。
読み直すかどうかは本人が押して決める。あわせて sw.js のHTML取得を
`cache:'reload'` にし、設定に現在のビルド番号を表示する。

### Why

`?v=guild-N` のキャッシュ対策は **index.html が読み直されたときしか効かない**。
ホーム画面に置いたPWAはアイコンを押しても前の画面を再開するだけでページを
読み直さないことがあり、ヨージのiPhoneが古い版のまま固定された（PCとcurlは
新しかった）。さらに GitHub Pages が `max-age=600` を付けるので、読み直しても
10分間は古いHTMLが返りうる。この2つを両方ふさぐ必要があった。

### Alternatives

- **見つけたら自動で読み直す** … 却下。ポモドーロ計測中に画面が飛ぶほうが
  被害が大きい。更新の遅れは数タップで取り返せるが、消えた集中時間は戻らない
- **version.json を作らず index.html を取って番号を読む** … 却下。54KB を
  再開のたびに落とすことになる。version.json は 24 バイト
- **サービスワーカーを消してキャッシュを一切やめる** … 却下。オフラインで
  起動できなくなる。PWAとして成立しなくなる
- **ヨージが毎回アプリを終了して開き直す** … 却下。人間の記憶に頼る運用は破れる

### Consequence

- `version.json` は **bump_version.sh が自動生成する**。手で書き換えないこと。
  index.html と番号がズレると、更新の案内が出っぱなし／出ないの事故になる
- sw.js は `vcheck` 付きURLと `version.json` を横取りしない（確認そのものが
  キャッシュから返ると、永遠に古い番号を見続けることになる）
- CACHE_NAME を v16 へ。古いキャッシュは activate 時に消える

## 2026-08-23 — 鳳凰の羽の救済マークは「学習記録」にはしない

### Decision

🪶鳳凰の羽を使うと、直前の空白日（最大7日・学習した日に当たったら打ち切り）に
専用の救済マーク「🪶守」がカレンダーへ付く。**history には一切書き込まない。**
そのため月の「学習日数」「学習時間」は増えず、完璧な週の判定にも入らない。

### Why

ヨージの要望は「使っても空白が埋まらないので何かマークを出してほしい」。
ただしアイテムで学習時間を書き込むと、カレンダーが「実際にやったことの記録」で
なくなる。roadmap の判断基準「努力を要求しない報酬を与えない」に真っ向から反する。
「やった日」ではなく「守られた日」として、見た目からして別物にすることで、
要望（空白が寂しい）と記録の正確さを両立させた。

### Alternatives

- **history にダミーの分数を入れる** … 却下。学習日数・累計時間・ベスト記録・
  完璧な週まで全部が嘘になる。あとから本物と区別できなくなるのが致命的
- **今日にもマークを付ける** … 却下。今日はこれから学習できる日。休んだ日として
  塗ってしまうと、その日の行動を止める方向に働く
- **今日にもマークを付ける** … 却下（盾も同じ）。盾は今日も保護対象に含むが、
  印だけは今日を外す。今日が終われば翌日から印が出るので、記録としては欠けない

### Consequence

- `gq_data` に `rescuedDays`（日付キー → 'phoenix' | 'shield'）を追加。新しい
  localStorage キーは作っていないので台帳の更新は不要、バックアップにも自動で乗る
- 「カレンダーに印は出るが集計は増えない」という状態が正になる。今後
  集計がズレて見えても、それは救済マークのぶんであってバグではない
- 既に印がある日は、あとから別のアイテムで守っても上書きしない（先に守った側の手柄）

### 追記（同日）— 守りの盾（🛡）も同じ仕組みに乗せた

ヨージの許可を得て盾も対応。🪶橙／🛡青で、どちらに守られたかが見て分かる。
盾の保護日は `gq_streak_shield_protected` にもあるが、**このキーは最新1回分しか

カレンダーは描画時に両方を読む（盾キーの読み取りは、この仕組みが入る前に

## 2026-08-23 — 名言の♡お気に入りを撤去（名言そのものは残す）

### Decision

名言機能を2つに分けて判定した。

- **残す**: 告（学習を終えた直後）に名言が1つ出る／📤コピー
- **撤去**: ♡お気に入りボタン、バッジ「💌 言葉コレクター」、称号「名言コレクター」

保存データ `gq_words_favs` は**消さない**（不可逆のため。UIを止めるだけ）。
到達不能な言葉コレクション画面（`words-overlay`）も今回は触っていない。

### Why

4基準で評価がきれいに割れた。

| 基準 | 告の名言 | ♡＋バッジ |
|---|---|---|
| ①本当の努力を要求するか | ⭕ 学習を終えた人にしか出ない | ❌ **押すだけでバッジと称号** |
| ②STARTまでの秒数 | ⭕ 影響なし | ⭕ 影響なし |
| ③余韻を奪わないか | ⭕ 余韻を作る側 | △ ボタンが1つ増える |

基準①違反はログインボーナス420XP→20XPと同じ構図。
さらに「集める楽しみ」はオトモン図鑑がすでに担っており、努力の要らない
コレクションを並置すると**安い達成感の逃げ道**になる。

### Alternatives

- **全撤去（名言ごと消す）**: 基準に合っている部分と257件の資産まで失う。却下
- **♡を残し、コレクション画面を復活（出会った言葉だけに絞る）**: 実装は可能
  （`gq_words_hist` に履歴がある）が、図鑑と役割が重複し機能過多。却下
- **♡だけ消してバッジは残す**: 永久に取れないバッジが残る＝
  「押せない理由が分からない」で、同日の掟に反する。却下

### Consequence

- 獲得数の集計を「いま定義されているバッジのうち獲得済み」に変更。
  撤去したidが `gq_badges` に残っていても数がズレない（データは消さない）
- バッジ総数 137 → **134**
- 副産物のバグ修正: `renderDailyQuote()` が表示先の無いまま毎起動 `pickQuote` を
  呼び、誰にも見られないまま「1週間は同じ言葉を出さない」プールを消費していた。
  表示先が無ければ拾わないように修正
- 復活防止のメモを index.html の告のマークアップに残した（装備・響く言葉と同じ形式）

## 2026-08-23 — 図鑑のセルのタップは「お供に設定」から「詳細を開く」へ

### Decision

オトモン図鑑の発見済みセルをタップしたら、**その子の詳細ビューを開く**。
お供の切り替えは詳細内の「🤝 お供にする」ボタンに移す。
未発見セルのタップは詳細を開かず、「まだ会っていないオトモンだよ」の1行だけ返す。

詳細に出すもの：絵・名前・レア度/属性/役割・なつき度ゲージ・フレーバー文・
出会った日/一緒に過ごした日数/学習時間/連続ふれあい・**解放済みのセリフ**。

### Why

- 図鑑は本来「見るもの」。タップで即お供が入れ替わるのは図鑑の動きとして不自然
- 事故防止：見たいだけのタップでお供が変わってしまうのを防ぐ
- 積み上げ（日数・時間・なつき度）を1か所で見せると、続ける動機になる

### Alternatives

- **タップ＝お供のまま、ⓘボタンで詳細**：セルが84pxしかなく押し分けが難しい。却下
- **タップで詳細を開きつつ同時にお供にする**：見たいだけの時に入れ替わる。却下
- **セリフを全段階見せる**：未解放分がネタバレになる。「響く言葉」を撤去したときと
  同じ理由で却下。解放済みのみ表示し、先は「？？？（「しんらい」で解放）」とする

### Consequence

- お供の切り替えに1タップ増える
- 100体中ほとんどが説明文・役割を持たないため、**無い項目は行ごと省略**する作りにした
  （「—」を並べない）。マスターデータを埋めれば自動的に濃くなる
- `BOND_TIERS` をデータ層から公開した（段階の順序がUI層で必要になったため）

## 2026-08-08 — プロダクトの理想とトーン

### Decision

Growth Quest の理想を次の一文に定める。

> **自己規律を作り、それを楽しみながら実行し、気がついたら成長している**

トーンについては、**規律を課すのはユーザー自身であり、アプリではない**とする。
アプリが担当するのは「楽しみながら実行できるようにすること」と
「気がついたら成長していたと実感させること」。

### 前提（重要）

**この理想は新しく決めたものではなく、2026-07-30 の決定の言い直しである。**
`docs/team/roadmap.md` §4 に、ヨージ本人の言葉としてこう記録されていた。

> これは成長を支援するツールでありたい。毎日開きたくなる、少しでも習慣化したり
> 頑張りたくなるような仕組みが散りばめられてる。
> **気がついたら楽しみながら成長してた**というのが目的。

同じ決定が9日前に存在したのに、13KBのロードマップに埋もれていたため見つからず、
今日ゼロから辿り直した。**これは DECISIONS.md が無かったことによる手戻りの実例。**
以後、この種の決定はここに集約する。

### 判断基準の関係

理想3フェーズと、roadmap §4 の4基準は**別々の物差しではない**。

- **理想3フェーズ** = なぜそう判断するのか（思想）
- **roadmap 4基準** = どう問うか（実際の判定質問）

機能の採否は4基準で問う。4基準で判定できないものだけ3フェーズに戻る。
対応関係は CONTEXT.md に記載。

### Why

「楽しみながら」と「自分を律する」は対立すると考えていたが、対立ではなかった。
規律の出どころをユーザー側に置けば、アプリは楽しさ側に専念できる。
この整理により、他人に配っても「休息や弱音を否定するアプリ」にならない。

### Alternatives

- **アプリ側が規律を提示・強制する**
  → 短期的な行動変容には効くが、押し付けになり「楽しみながら」と両立しない。
    また他人に配ったとき、疲れている人を追い詰めるため却下
- **楽しさだけを提供する（規律要素を持たない）**
  → 「気がついたら成長している」に届かない。ただの娯楽になるため却下

### Consequence

- **機能の判断基準**が「自己規律を作る／楽しく実行する／成長を実感する」の
  3つに効くかどうかになる。どれにも当たらない機能は作らない
- デフォルトのクエストや目標を押し付けない。提案はするが選択は本人
- ナッジは「命令」ではなく「思い出させる」設計にする
- 楽しさは事後の報酬より、**始める摩擦の低減**に重点を置く
- **日々の画面で成長を突きつけない。** 数値や達成度の強調は
  振り返り側（カレンダーレビュー等）へ寄せる
- roadmap §4 の4基準を CONTEXT.md へ転記した（毎回13KBのロードマップを開かないため）。
  **どちらかを変更したら両方を揃える**

## 2026-08-08 — プロダクトのスコープ

### Decision

Growth Quest のスコープは「学習アプリ」ではなく、**成長を促す生活習慣アプリ**とする。
学習はその中の一ジャンルという位置づけ。

### Why

CONTEXT.md の行動指針には、遅刻・片付け・食習慣・浪費・対人態度など
学習以外の領域が多く含まれている。ヨージが本当に変えたいのは学習習慣だけではない。
長期目標も「みんなが成長を楽しみながら続けるためのツール」であり、学習に限定していない。

### Alternatives

- **学習アプリに限定する**
  → 機能の焦点は絞れるが、行動指針の大半が対象外になり、
    「自分が毎日開くアプリ」という今年の目標を満たしにくいため却下
- **決めずに進める**
  → 機能を作るか迷うたびに判断がぶれるため却下

### Consequence

- クエストの対象が学習以外へ広がる（生活・健康・時間管理・対人など）
- **計測できる行動（時間で測れる）と、できない行動（やった/やらないのみ）の
  2種類を扱う必要が出る。** 現状はタイマー＝時間計測が中心のため、設計上の分岐点になる
- **「〜しない」型の目標をどう扱うかが課題になる。**
  行動指針の多くは「〜しない」形だが、アプリは「〜した」を貯める設計。
  達成しても何も起きない行動には報酬設計が効かない
- CLAUDE.md / AGENTS.md / README.md の説明文
  「学習をゲームのように続けるためのブラウザアプリ」を更新する必要がある
- 比較対象が学習系アプリから習慣系アプリへ移る

## 2026-08-08

### Decision

AI運用基盤（docs/AI/）を導入した。ただし当初計画していた Obsidian の
PARA構造（00_Inbox / 10_Goals / 20_Projects …）の全面導入は却下し、
docs/AI/ に5ファイルを追加、CLAUDE.md / AGENTS.md には追記のみとした。

役割の割り当ては以下に確定：
- ChatGPT = 企画・優先順位・文言・仕様の目的妥当性チェック（コード不要の仕事すべて）
- クロ = コードベース調査・設計・仕様書作成・差分レビュー・小さな修正
- Codex = 仕様書ベースの実装量産
- スクリプト = 機械的検証（トークンゼロ）

### Why

1. 既存の CLAUDE.md / AGENTS.md には、実際の事故から得た知見
   （guild-141 の起動フリーズ、check_load_order.py、bump_version.sh）が入っており、
   汎用テンプレートより価値が高い。上書きは損失になる
2. docs/ は既に spec_*.md 25本の発注書置き場として機能しており、
   PARA構造を被せると動いている仕組みを壊す
3. コード約333kトークン＋docs約184kトークンで、全体を読めるAIは存在しない。
   よってコンテキストの節約が最優先事項になる

### Alternatives

- **PARA構造を docs/ に全面導入**
  → 既存の発注書ワークフローと二重管理になるため却下
- **CLAUDE.md をテンプレートで置き換え**
  → 実事故ベースの知見が失われるため却下。追記のみとした
- **別Vaultを新規に作る**
  → docs/ と二重管理になり、AIがどちらを見るべきか曖昧になるため却下
- **記録を人間が手動で書く**
  → 作業終了時（最も面倒な瞬間）に依存するため、必ず途切れると判断。
    記録はクロの通常業務とした

### Consequence

- クロは作業開始時に docs/AI/CURRENT.md を読む
- レビューは git diff と受け入れ基準のみで行う（全ファイル再読み込みは禁止）
- 1ファイル50行以下の修正は仕様書を書かずクロがその場で対応する
- コードを必要としない仕事は ChatGPT へ回す
- 仕様書を書いた後・実装前に、ChatGPT へ目的妥当性を1回通す
  （クロが仕様も書きレビューもする構造の穴を埋めるため）
