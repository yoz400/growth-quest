## 2026-08-24 — 「1つの条件で試してOK」は検証になっていない（週ごとの1体が全部同じ）

### 事象

完璧な週の相棒を「週に1体・週ごとに変わる」にした。誰が来るかは
`日付キーのハッシュ % 手持ちの数` で決めていた。プレビューで
**手持ち5体**で試し、週ごとに違う子が出るのを確認してデプロイ。
ヨージの実機では**全部同じ子**だった。

原因は数の性質。カレンダーの週の先頭は 09 → 16 → 23 と並び、
素朴なハッシュ（`h*31 + 文字コード`）だと隣り合う週の差が**いつもきっかり28**。
28 は 2・4・7 で割り切れるので、**手持ちが2体・4体・7体だと同じ月の週が全部同じ子**
になる。たまたま5体で試したので（28 % 5 = 3）一度も再現しなかった。

### なぜ気づけなかったか

「52週ぶん試して偏りなし」という**それらしい数字を1つ出して満足した**。
だが変えていたのは週だけで、**手持ちの数は5に固定**していた。
剰余を使う設計なら、割る数（＝手持ちの数）こそ動かすべき変数だった。

### 再発防止（ルール）

- **`% n` を使う設計は、n を 1〜12 くらい全部で試す。** 剰余の事故は
  特定の n でだけ出る。1つの n で通っても何の保証にもならない
- 「週ごとに違う」のように**保証したい性質**があるなら、確率（ハッシュ）に
  頼らず**順ぐりに回して構造で保証する**。いまは通算週番号 + 年ごとの
  ずらしで、隣の週とは必ず別の子になる（`pickRunnerForWeek`）
- 検証コードは**入力の全パターンを回して合否を出す**。目視で1例を見て
  「良さそう」で終わらせない

## 2026-08-24 — 検証で手を貸してしまい、本番だけ壊れていた（読み込み順の穴）

### 事象

完璧な週の相棒を「手持ちオトモン最大4体」にして、プレビューで4体走るのを
確認してデプロイした。ヨージの実機では **導きの妖精のまま何も変わらなかった**。

原因は読み込み順。`otomon.js` は `calendar-review.js` より**後**に読まれるが、
起動時の `renderCalendar()` は `boot.js`（otomon.js より前）から走る。
そのとき `window.Otomon` はまだ存在せず、フォールバックの妖精が描かれる。
そして通常の操作では二度と再描画されないので、妖精のまま固定される。

### なぜ気づけなかったか

**検証のたびに、自分で `window.renderCalendar()` を呼んでいた。**
プレビューのスクロールが効かずカレンダーを表示できなかったので、
手で描き直していた。その時点では otomon.js の読み込みが終わっているため、
4体が正しく出る。**アプリが自力で描いた結果を、一度も見ていなかった。**

`tools/check_load_order.py` も素通しした。あれが見つけるのは「裸で呼んでいる」
呼び出しで、今回のように `window.Otomon &&` で**守られた参照は落ちずに
静かに劣化する**。ツールの守備範囲外だった。

### 再発防止（ルール）

1. **検証で状態を手作りしない。**「アプリが自分で描いたDOM」を読む。
   `renderX()` を手で呼ぶのは、その1回の描画だけを見たいときに限る。
   呼んだなら、**呼ばない経路でも同じ結果になるか**を必ず別途確かめる。
2. **後から読まれるファイルの機能を使う描画は、起動時に間に合わない**と疑う。
   `window.Xxx &&` のガードは、落ちない代わりに「静かに違うものを描く」。
   ガードで済ませず、**用意ができたら描き直す**まで書く
   （`waitOtomonThenRedraw()` in calendar-review.js）。
3. `check_load_order.py` は**裸の呼び出ししか見つけられない**。
   ガード付きの参照は自分で追う。

## 2026-08-23 — inert事故はまた起きた。「出す瞬間に見る」だけでは足りない

### 事象

更新のお知らせ帯（`#update-bar`）を追加した。CURRENT.md の申し送りを読み、
`#review-prompt` と同じく「出すときに `Overlay.topId()` を見て、モーダルが
開いていたら1秒後に再挑戦」というガードを入れた。それでも帯は
**召喚オンボーディングの上に出て、inert を浴びて押せなくなった**
（`bar.inert === true`／`elementFromPoint` が `summon-overlay` を返すのを計測）。

原因は順番。帯を出した時点ではモーダルは開いていなかった。
**そのあとでモーダルが開いた**。一度きりの判定では、この向きの事故は防げない。

### なぜ気づけなかったか

`#review-prompt` の対策をそのまま真似た。だが `#review-prompt` は
「起動から2.2秒後に1回だけ出す」もので、`#update-bar` は
「アプリに戻ってくるたび／いつでも出る」もの。**寿命の長さが違う**のに、
同じガードで足りると思い込んだ。

### 再発防止（ルール）

body直下・position:fixed の浮き要素で、**操作部品を持つもの**を足すときは、
出す瞬間の1回判定ではなく **見張り続ける**こと。

```js
// 出したい状態（_pending）を持ち、モーダルの開閉を定期的に見て出し入れする
if (!_keeper) _keeper = setInterval(sync, 800);
function sync() {
  const open = !!Overlay.topId();
  bar.classList.toggle('show', !!_pending && !open);
}
```

検証は「モーダルを開いてから帯を出す」だけでなく、
**帯を出してからモーダルを開く**順番も必ず試す。
判定は見た目ではなく `el.inert` と `document.elementFromPoint()` で行う。

## 2026-08-23 — 4体並べたのに1体しか見えない（同じ軌道に完全に重なっていた）

### 事象

完璧な週で走る相棒を1体→最大4体に増やしたが、画面には1体しか居ないように見えた。
DOM には4体ちゃんと居て、画像も4種類とも読めていた。原因は全員が同じ
`@keyframes pwMove`（left 4%→88%）に乗り、同じ高さ・同じ速さで走っていたこと。
ぴったり重なると、要素が増えても見た目は1体のまま。

さらに検証中のブラウザが `prefers-reduced-motion: reduce` だったため、
app.css 末尾の全体ルール（`animation-duration: .01ms !important`）で動きが
潰され、4体が同じ座標に固まっていた。**アニメで散らす設計は、アニメを切って
いる人には効かない。**

### なぜ気づけなかったか

「要素が4つ生成されているか」を DOM で確認して満足した。
数が合っていても、座標が同じなら見え方は1つ。**目視のスクショを撮るまで
「増えた」と判断してはいけない。**

### 再発防止（ルール）

同じ animation を複数要素に付けるときは、必ず次の2つをセットで散らす:

1. **動いているときの軌道** … keyframes の値を CSS 変数にして
   （例 `left: var(--pw-from, 4%)`）、要素ごとに JS から別の値を渡す
2. **止まっているときの位置** … inline style で `left` 等を要素ごとにずらす。
   `prefers-reduced-motion` ではアニメが即終了し、fill-mode が無ければ
   非アニメ時のスタイルに戻るので、ここが最終的な見た目になる

検証は DOM の個数ではなく、**スクリーンショットで実際に散っていること**を見る。

## 2026-08-23 — 「タップしても反応しない」は、実装バグではなく無反応セルだった

### 事象

「オトモン図鑑のセルをタップしても何も起きない」とバグ報告を受けた。
調査した結果、**コードの配線は全て正常**だった。ヨージが押していたのは
未発見（？？？）のセルで、そこには最初から click リスナーが無かった。

### 原因

未発見セルは `data-otomon` を持たず、リスナーの対象外。
そして押しても**何の反応も返さない**（メッセージも見た目の変化も無い）。
100マス中95マスが無反応マスだったため、適当に押せばほぼ確実にそちらに当たる。

**ユーザーには「仕様で押せない」と「壊れて押せない」が区別できなかった。**

### 兆候

「開くけど中が効かない」という報告は、
**実装の断線ではなく "そこは元々押せない" の可能性**を先に疑う。
再現環境で普通に動いてしまったら、まずユーザーの操作対象を特定する。

### 再発防止

- **仕様**: 押せない要素は必ず「押せない理由」を返す（無言で沈黙させない）。
  図鑑の未発見セルは「まだ会っていないオトモンだよ」を表示するようにした（guild-160）
- **切り分け手順**: 実機バグ報告は
  ①コンソール不要で目視できる質問に落とす（件数・文言の有無・見た目）
  ②再現環境で動いたら「押した対象」を図で確認する
  この2段でヨージへ聞く。今回は「？？？のマスと絵入りのマス、どちらを押したか」で確定した

## guild-141 — 本番が起動不能になった（読み込み時参照 / TDZ）

### 事象

本番環境でアプリが起動しなくなった。しかも全員ではなく
**「ナッジコースを選んでいる人」にだけ**発生した。

### 原因

前に読み込まれるファイルから、後に読み込まれるファイルの関数を
「読み込み時点で裸で」呼んでいた。

function宣言の巻き上げはファイル内でしか効かない。
let/const は TDZ（宣言行より前で触るとエラーになる期間）があるため、
`typeof` によるガードも効かない。

### 兆候

- 同種の事故は**これで3回目**だった
- 3回とも**目視レビューでは発見できなかった**
- `localStorage.clear()` から始めるプレビュー検証では**一度も再現しなかった**

### 再発防止

- `tools/check_load_order.py` を作成。JSを編集したら必ず実行する（数秒）
- コールバックは必ず `() => fn()` で包む
- **条件付きで走る経路は、条件を作らないと踏めない。**
  プレビューでの正常動作は「検証した」ことにならない
- CLAUDE.md / AGENTS.md の「開発の掟」2番に明記済み

## 「直したのに直ってない」 — キャッシュバスターの更新漏れ

### 事象

CSS / JS を修正しても、ブラウザに変更が反映されない。
「さっき直したはず」の症状が続き、原因究明に時間を溶かす。過去に何度も発生。

### 原因

`?v=guild-N` のキャッシュバスターを更新していないため、
ブラウザが前回のファイルを使い回していた。

### 兆候

コードは明らかに直っているのに、画面だけが古い。

### 再発防止

- `bash tools/bump_version.sh` で一括+1する
- CSS/JS を編集したら**必ず**実行。CLAUDE.md / AGENTS.md の掟1に明記済み
