## 1. このアプリが死ぬ5つのシナリオ

### 💀 シナリオ1: 「PWAだと思っていたものが、実は動いていない」（確率: 高）

**すでに壊れています。半年後ではなく、今。**

`sw.js` は Service Worker（＝オフラインでもアプリを動かすための裏方プログラム）です。
その 12行目にこう書いてあります。

```javascript
// sw.js:8-13
const PRECACHE_URLS = [
  './',
  './index.html',
  './styles/app.css',
  './scripts/app.js',      // ← このファイルは存在しない
  './manifest.json',
```

`scripts/app.js` は **コミット `c70c9ee`「Remove split app script」で削除済み**です
（`ls scripts/app.js` → No such file or directory）。

そして `sw.js:62` の `cache.addAll(PRECACHE_URLS)` は**オール・オア・ナッシング**です。
リスト内の1つでも404になると、Promise 全体が失敗します。

```text
install イベント
   ↓
cache.addAll([... './scripts/app.js' ...])
   ↓
404 → 配列ごと失敗
   ↓
waitUntil が reject
   ↓
Service Worker は activate されない ＝ 一度も動かない
```

**帰結:**
- オフラインで開くと真っ白（キャッシュが1つもない）
- ホーム画面に追加した「アプリ」は、電波が無いと起動しない
- しかも `index.html:978` の `.catch(err => console.warn(...))` で
  **警告レベルに握りつぶされている**ので、誰も気づかない

さらに `PRECACHE_URLS` には、分割後の9本のJS（core.js〜otomon.js）が**1本も入っていません**。
仮に `app.js` の行を消しても、オフライン起動はやはり不可能です。

> ⚠️ 私はブラウザを触らない担当なので、実機での最終確認は検証担当に回してください。
> 確認方法: DevTools → Application → Service Workers に「activated」が出るか。

### 💀 シナリオ2: 「褒めログだけが、静かに消える」（確率: 高）

エクスポート機能（＝記録の書き出し）はこうなっています。

```javascript
// scripts/settings-genre.js:101-104
for (let i = 0; i < localStorage.length; i++) {
  const k = localStorage.key(i);
  if (k && k.startsWith('gq_')) out.data[k] = localStorage.getItem(k);
}
```

`gq_` で始まるキーだけを書き出しています。
ところが保存キーは全部で51個あり、そのうち**1個だけ `gq_` で始まりません**。

```javascript
// scripts/progression.js:249
try { return JSON.parse(localStorage.getItem('growthPraiseLogs') || '{}'); }
```

`growthPraiseLogs` — **褒めログ**です。「今日はここが良かった」を毎日書き溜めた、
このアプリで**いちばん取り返しがつかないデータ**。数字は再現できても、その日の言葉は再現できません。

これは `docs/architecture_review.md:112` に
「⚠️唯一の命名違反・既存データのため改名不可」と**書いてあるのに**、
同じ文書の §4-掟5「exportAllData() の対象に含める」が守られていない。
**掟が自分の例外を見落としている**という、いちばんタチの悪い形の穴です。

インポート側（`settings-genre.js:123`）も `filter(k => k.startsWith('gq_'))` なので、
仮にファイルに入っていても**復元されません**。往復どちらも通れない。

### 💀 シナリオ3: 「2週間の旅行から帰ったら、全部消えていた」（確率: 中）

localStorage は**ブラウザが勝手に消せる場所**です。消える経路は3つ。

```text
経路A  Safari の ITP（トラッキング防止機能）
       → ホーム画面に追加していない状態で「7日間サイトを開かない」と
         スクリプトが書いた保存領域を削除する
       → 入院・出張・旅行・繁忙期。2週間空けたら終わり

経路B  「履歴とサイトデータを消去」を押す
       → 別の目的（広告が重い、動作が変）でやった1クリックで全消し

経路C  端末の買い替え・機種変更
       → localStorage は端末の中だけ。何もしなければ引き継がれない
```

これに対する備えは「設定 → ⬇エクスポート」ボタン1個だけ（`index.html:761`）。
**バックアップを促すリマインドがコードのどこにもありません**
（`grep -rn "バックアップ" scripts/` の結果はエクスポート関数の中だけ）。

つまり守りが「ヨージが自発的に思い出す」ことに100%依存している。
1年続けたアプリのデータ保護としては、これは対策と呼べません。

さらに `saveData()` は例外処理ゼロです。

```javascript
// scripts/core.js:258-261
function saveData(d, reason = 'saveData') {
  localStorage.setItem('gq_data', JSON.stringify(d));   // try/catch なし
  GQ.emit('data:changed', { reason });
}
```

容量オーバーやプライベートブラウズで `setItem` が例外を投げると、
`completeSession()`（`timer.js:414`）の途中で処理が止まり、
**XPは入ったのにセッションが記録されていない**といった中途半端な状態になります。

### 💀 シナリオ4: 「レベルバーが、もう動かない」（確率: 高／半年後の本命）

XPの設計を数式で追います。

```javascript
// scripts/progression.js:66
function xpForLevel(lv) { return lv * 100; }
// scripts/progression.js:71
data.xp += Math.round(minutes * getActiveXpMultiplier());   // XP = 学習した分数
```

XP は「学習した分数」そのもの。次のレベルに必要なXPは `レベル × 100`。
つまり **レベルNに到達するまでの累計 = 50 × N × (N-1) 分**。

| 目標レベル | 必要な累計学習時間 | Lv到達に必要な"次の1レベル分" |
|---|---|---|
| Lv 5 | 約 17時間 | 6.7時間 |
| Lv 10 | 約 75時間 | 15時間 |
| Lv 20 | 約 317時間 | 32時間 |
| Lv 30 | 約 725時間 | 48時間 |

```text
Lv1→2    ■ 100分（1時間半）        ← 初日で上がる。楽しい
Lv9→10   ■■■■■■■■■ 900分（15時間） ← 1〜2週間かかる
Lv19→20  ■■■■■■■■■■■■■■■■■■■ 1900分（32時間） ← 1か月動かない
```

**ゲームの報酬が効かなくなる瞬間**が、設計上ここに埋め込まれています。
1日1時間ペースなら、半年後（Lv20前後）には「バーがほぼ動かない」。
これが「半年後に使われなくなる」の**いちばん直接的な数学的根拠**です。

しかも報酬倍率アイテム（`core.js:405` `getActiveXpMultiplier`）があるので、
XPは**もはや学習時間を正しく表していません**。同じ25分が、アイテム次第で違う値になる。
指標としても壊れ始めています。

## 4. 反論可能性（自分でも弱いと思う点）

批評家として、自分の主張の弱いところを先に書きます。

1. **「機能過多」という批判自体が的外れかもしれない。**
   このアプリのユーザーは1人（ヨージ）で、**作ること自体が目的の可能性**があります。
   もしプログラミング学習の教材として作っているなら、機能が多いことは欠点ではなく成果です。
   その場合、私の削減提案はまるごと無意味になります。
   → **ヨージ自身が「これは学習ツールか、制作物か」を決めてくれないと、この章は判定不能です。**

2. **アンダーマイニング効果の話は、証拠が弱い。**
   「報酬が内発的動機を壊す」は有名な理論ですが、**自分で自分に与える報酬**では
   効果が出にくいという研究もあります。私はコードは読めますが、
   ヨージの学習時間が増えたか減ったかは知りません。
   → 判定材料は既にアプリの中にあります。`gq_data.history` の月別合計を見れば、
     **機能を足した月に学習時間が伸びたのか減ったのか**が分かる。それが唯一の証拠です。

3. **Lv20で伸びが止まる件は、「止まっていい」かもしれない。**
   `xpForLevel = lv * 100` の線形設計は、実は多くのゲームより緩やかです。
   そして「累計学習1200分」という数字自体が報酬になる人もいる。
   私は「バーが動かない＝つまらない」と決めつけていますが、これは仮説です。

4. **PWA が壊れている件は、実害がゼロの可能性がある。**
   ヨージが常時オンラインで使っているなら、Service Worker が動かなくても何も起きません。
   ただし**「壊れていることに1か月以上誰も気づいていない」という事実の方が問題**です。
   気づけない仕組みで運用している、という指摘は取り下げません。

5. **削減提案には、私が背負わないコストがある。**
   すごろくを削るには7キーの整理とデータ移行が必要です。私はコードを書かない担当なので、
   その痛みを見積もっていません。「削れ」と言うのは簡単です。

## 5. それでも守るべき核 — ひとつだけ

**「まず5分だけ」からタイマーのSTARTを押せること。それだけは絶対に壊すな。**

```text
このアプリの本体はこの3行だけ:

    ジャンルを選ぶ  →  STARTを押す  →  25分たつ
                                        ↑
                          ここまでが「学習が続く」の全部。
                          これより後ろは全部おまけ。
```

具体的に、この核を守るために**触ってはいけない場所**：

- `timer.js` の壁時計方式（`Date.now()` 差分での計測）
  — バックグラウンド・リロード・スリープに強い。ここは本物の技術資産です
- `index.html:154` の START ボタンが、**アプリを開いて1タップ以内**にあること
- `UNLOCK_DEFS`（`boot.js:73-81`）の段階解放
  — 新規ユーザーが最初に見るのが「妖精・ジャンル・設定」の3つだけ、という抑制

そして**新機能を足すときの唯一の基準**を提案します。

> ### 「STARTを押すまでの秒数が伸びるなら、その機能は入れない」

XPも、オトモンも、ギルドも、名言も、すごろくも、
**STARTを押した"後"に置く限り無害**です。
危険なのは、それらがホーム画面に降りてきて START の前に立つ瞬間。

現時点でホームには7枚のカードがあります（`grep -c "glass widget" index.html` → 7）。
今日のクエスト／使命／今日の予定／ジャンル／タイマー／統計／打刻。
**タイマーは既に5枚目です。** ここが半年後の生死を分けます。
