### P0-1. 主役ボタン START が、初回起動時に画面1枚分下にある

**根拠**

- DOM順（`index.html`）: ヘッダー(61) → はじめの一歩(108) → 今日のクエスト(121) → 使命(129) → 今日の予定(136) → **ジャンル(145) → タイマー(152)**
- さらに `otomon.js` が **`#daily-quest-card` の直後に3枚**割り込ませる: 卵カード(`otomon.js:1220-1230`) / オトモンクエスト(`1525-1535`) / お供オトモン(`1458-1468`)
- 余白: `#app { padding:16px; gap:14px }`(`app.css:92-98`)、`#app .widget { padding-top:30px }`(`app.css:61`)
- タイマーカードは中身の頭に `#anim-stage { width:220px; height:220px }`(`app.css:225-228`) があり、STARTはさらにその下

**積み上げ計算（新規ユーザー・iPhone想定）**

```text
  16px  #app の上余白
+150px  ヘッダー（ロゴ行 / アイコン8個の行 / XPバー が折り返して3段）
+ 14    gap
+182px  はじめの一歩カード
+ 14
+193px  今日のクエストカード
+ 14
+ 98px  ジャンルカード
+ 14
────────────────────────────
 695px  ← ここでやっと「タイマーカードの上端」
+ 30px  widget の上余白（つまみ帯）
+220px  アニメーション（焚き火・植物など）
+ 20px  gap
────────────────────────────
 965px  ← START ボタンの上端

iPhone 14 / Safari の見えている高さ ≒ 700px
```

**なぜ問題か**

`index.html:117` は新規ユーザーにこう言っています ──「**まずは下の光ってる START を押してね**」。
ところがその光っているボタン(`app.css:4156` `#start-btn.first-glow`)は**画面の外**にあり、
起動時の自動スクロールもありません（`scrollIntoView` は `features.js:369/426/607/728` にあるが、
すべて**妖精ガイドや初回ツアーからの呼び出し**で、通常起動時には走らない）。
初回ツアーをスキップした人・2日目以降に開いた人は、毎回「まず下へスクロールする」が仕事になります。

**直し方（コスト小・3案。上から推奨）**

- **A案:** DOM順を「タイマー → クエスト → その他」に変える。`index.html` のカードのブロックを移動するだけ。
  併せて `boot.js:1238` の `KNOWN_IDS` のデフォルト順も同じ順に。
- **B案:** 起動時に、初日〜3日目のあいだだけ `timer-card` へ自動スクロール。
  既に同じコードが `features.js:426` にあるので流用できる。
- **C案:** アニメーション枠 220px は「集中中の演出」なので、**待機中は 96px に縮める**。
  それだけで START が 124px 上がる。

### P0-2. PWAでヘッダーがiPhoneのステータスバーに潜る

**根拠**

- `index.html:26-28`：`apple-mobile-web-app-capable = yes` かつ `apple-mobile-web-app-status-bar-style = black-translucent`
- `styles/app.css` 全体で `safe-area-inset` の出現回数 **0件**
- `#app { padding:16px }`(`app.css:92-98`) が唯一の上余白

**なぜ問題か**

> **セーフエリア** とは：iPhoneの「時計や電池が出ている帯」「下の細い横棒（ホームインジケータ）」に
> かぶらないための安全地帯のこと。`env(safe-area-inset-top)` という値で「何px避ければいいか」を教えてもらえます。

`black-translucent` は「Webの中身をステータスバーの**下まで**描いてよい」という宣言です。
つまり、ホーム画面に追加して開くと、上から約47〜59pxぶんが時計と電池に**重なります**。
ヘッダーは `#app` の一番上（`index.html:61`）なので、**ロゴ・アバターボタン・アイコンナビの1段目が
時計の下に隠れる**ことになります。下側も同様に、カレンダーの最終行がホームインジケータに触れます。

「PWA対応・ホーム画面追加OK」を売りにしている(`index.html:20-32`)以上、これは信頼を直接損ないます。

**直し方（コスト極小・CSS 3行）**

```css
#app {
  padding: calc(16px + env(safe-area-inset-top, 0px)) 16px
           calc(16px + env(safe-area-inset-bottom, 0px));
}
```

（`env()` は非対応環境では第2引数の `0px` が使われるので、PC版は一切変わりません）

### P0-4. 最頻出モーダル「世界樹の妖精」が縮んでズレたまま出ている

**根拠**

```
app.css:2258  .gq-panel { transform: scale(.95) translateY(20px); }   ← 常にこの状態
app.css:2262-2274  #genre / #settings / #badges / #words / #avatar / #review /
                   #guild / #skill / #board / #equipment / #equipment-get /
                   #tutorial / #praise の 13個だけ  .open 時に transform: none
```

この13個のリストに入っていないのに `class="gq-panel"` を持つパネル:

| パネル | 場所 | 自前のtransform | 結果 |
|--------|------|----------------|------|
| `#fairy-panel`（世界樹の妖精） | `index.html:891` / CSS `app.css:3709-3715` | **無し** | 常時 5%縮小 + 20px下ズレ |
| `#otomon-panel`（オトモン図鑑） | `otomon.js:1238` / CSS `otomon.js:1063` | **無し** | 同上 |
| `#fairy-guide-panel` | `index.html:910` | `app.css:4291` で個別に打ち消し済み | 正常 |

**なぜ問題か**

`#fairy-panel` は「セッションを終えるたび」に出る、**このアプリで最も多く見られるモーダル**です
（`progression.js:417` から呼ばれる）。それが他のモーダルと違う大きさ・違う位置で出続けている。
一つ一つは「なんか安っぽい」程度の違和感ですが、**毎回**なので効きます。

そして `#fairy-guide-panel` にだけ個別の打ち消しが書かれている(`app.css:4291`)ことが、
**この「IDを列挙する方式」が過去にも漏れを起こした証拠**です。3枚目・4枚目も必ず漏れます。

**直し方（コスト極小・発想を逆にする）**

```css
/* いまの発想：「デフォルトは縮み。開いたIDだけ元に戻す」 → 列挙漏れが起きる  */
/* 変える発想：「デフォルトは正常。閉じている間だけ縮む」 → 漏れが起きえない  */
.gq-panel { transform: none; transition: transform .35s cubic-bezier(.175,.885,.32,1.275); }
[id$="-overlay"]:not(.open) .gq-panel { transform: scale(.95) translateY(20px); }
```

（`[id$="-overlay"]` は「idが -overlay で終わる要素」という意味の書き方です）

### P1-1. ホームが最大14枚のカード置き場になっている（＝機能の墓場）

**根拠**

`#app` 直下に置かれるカードの実数:

| 出どころ | カード |
|----------|--------|
| `index.html` 10枚 | ヘッダー(61) / はじめの一歩(108) / 今日のクエスト(121) / 使命(129) / 今日の予定(136) / ジャンル(145) / タイマー(152) / 統計(197) / 打刻(215) / カレンダー(223) |
| `otomon.js` 3枚 | 卵(1220) / オトモンクエスト(1525) / お供(1458) ── **すべて `#daily-quest-card` の直後**に挿入 |
| `index.html` バナー1枚 | 休憩バナー(190) |

さらに並べ替えの仕組み(`boot.js:1232-1290`)には2つのズレがあります:

- `KNOWN_IDS`(`boot.js:1238-1240`) に **`'xp-panel'` と `'mode-panel'` が残っている**が、
  この2つは `index.html` に既に存在しない（ヘッダーXPとタイマーカードに統合済み）。＝**幽霊エントリ**
- otomon の3枚は `.widget` クラスを持たないので並べ替え対象外。
  並べ替えは `app.appendChild(el)`(`boot.js:1279`) で対象を末尾へ移す実装なので、
  **一度並べ替えると otomon の3枚だけが上に取り残され、意図しない配置になる**

**なぜ問題か**

前回レポートの評価軸「毎日開きたくなるか」で言うと、いま開いて最初に見えるのは
**「今日のクエスト」と「ジャンル選択」**です。どちらも「作業の前振り」であって、
**達成感でも、次の一歩でもない**。そして本命のタイマーは見えない（P0-1）。

カードが14枚あること自体が悪いのではなく、**14枚が全部フラットに縦積みで、
優先度の差が視覚的にゼロ**なのが問題です。

**直し方 ── 三層モデル**

```text
│ ⚡ オトモンクエスト │     3枚割り込み    │   ・クエスト/予定/打刻を       │     折りたたみ
│ 🤝 お供オトモン    │                    │     タブで1枚に統合           │     可
├───────────────┤                      ├─────────────────────────────┤
│ 使命               │                      │ 📚 ふりかえり                │  ← 第3層「記録」
├───────────────┤                      │   ・統計 / カレンダー          │     いちばん下
│ 今日の予定         │                      │   ・卵/お供は「相棒」1枚に統合  │
├───────────────┤                      └─────────────────────────────┘
│ ジャンル           │
├───────────────┤                      考え方：
│ ⏱ タイマー ★本命  │  ← ここが          「いま何をするか」＝1つだけ大きく
├───────────────┤     965px下         「今日の段取り」＝まとめて1枚
│ 統計               │                    「過去の記録」＝下でいい
├───────────────┤
│ 打刻               │                    otomonの3枚は「相棒」カード1枚に畳み、
```

3. タイマーを先頭へ（P0-1のA案と同じ作業）

### P1-2. 新規ユーザーのヘッダーが「？？？」だらけ＋コントラスト2.05:1

**根拠**

- ヘッダー8ボタン中4つが初期状態で `feat-locked`: `index.html:74`(ギルド) / `77`(すごろく) / `80`(スキル) / `83`(レビュー)
- ラベルは `boot.js:90` で **`'？？？'` に置換**される
- 見た目: `app.css:4068-4076`

```css
.header-right .feat-locked          { opacity: .5; }                     /* ← 4070 */
.header-right .feat-locked .icon-btn-emoji { filter: grayscale(1) brightness(.45); }
.header-right .feat-locked .icon-btn-label { color: rgba(255,255,255,.48); } /* ← 4075 */
```

**コントラスト計算（WCAG基準）**

`opacity: .5` は**要素まるごと**にかかるので、ラベル色の `.48` と**掛け算**になります。

```
実効の白 = 0.5 × 0.48 = 0.24
合成色   = 0.24×255 + 0.76×10(背景#0a0a0f) ≒ RGB(69,69,69)
背景     = #0a0a0f
────────────────────────────────
コントラスト比 ≒ 2.05 : 1     （WCAG AA の基準は 4.5:1）
```

さらにラベルのフォントサイズは `.5rem = 8px`（`app.css:153`）。
**8pxで2.05:1** は、実質「読めない」と同義です。

**なぜ問題か**

前回レポート P1-1 の指摘（空白のすき間 → ？で見せる）は**正しく実装されました**。
ですが「？？？」という文字列は「わからない」であって「**まだ見ぬ楽しみ**」ではありません。
新規ユーザーが最初に見るヘッダーは、いま実質こう見えています ──

```text
【いまの見え方】読めない灰色が4つ並ぶ
[🧚妖精] [▪️???] [▪️???] [▪️???] [▪️???] [📚ジャンル] [🥚オトモン] [⚙設定]
          ↑ グレースケール+輝度45%+不透明度50% ＝ ほぼ見えない
          ↑ ラベルは8px・コントラスト2.05:1 ＝ 読めない

【提案】ロックされた4つを1つの「予告カード」にまとめる
[🧚妖精] [🥚オトモン] [📚ジャンル] [⚙設定]      ← 常時使う4つだけ
┌──────────────────────────────────┐
│ 🔒 あと1回集中すると、2つの扉がひらきます      │  ← ホーム上部に細い帯
│    🏰 冒険者ギルド ／ 🎲 すごろく             │     解放されたら消える
└──────────────────────────────────┘
```

**直し方**

- 最低限（コスト極小）: `opacity:.5` をやめ、ラベル色を `rgba(255,255,255,.62)` の**一本**にする。
  フォントサイズを `.5rem → .62rem`(10px) に。→ コントラストが約 4.6:1 になりAA達成。

  ヘッダーが4つになるので P1-3 も同時に解決する。
- 文言: `'？？？'` → `'あと1回'` のように、**あと何をすれば開くか**をラベルそのものにする
  （情報は既に `UNLOCK_DEFS` の `hint`(`boot.js:74-80`)に全部ある）。

### P1-3. ヘッダー8ボタンが375px端末で1つ約31pxまで潰れる

**根拠**

```

```

375px端末での計算:

```
375 − #app左右余白32 − header左右余白36 = 307px（ヘッダー内の使える幅）
307 − gap 8px × 7 = 251px
251 ÷ 8ボタン ≒ 31px 幅
```

Apple のガイドライン 44pt、Google の 48dp を**どちらも大きく下回ります**。

**なぜ問題か**

「実際の利用はスマホが主」であり、しかも潰れているのは**設定・ジャンル・オトモン**という
毎日触る導線です。誤タップは「壊れている」印象に直結します。

**直し方**

- 本命: P1-2 と合わせてヘッダーを **4ボタン**に減らす（🧚妖精 / 🥚オトモン / 📚ジャンル / ⚙設定）。

  ギルド・すごろく・スキル・レビューは、既にある「導きの妖精」ガイド(`features.js:501-524`)が
  **すべて「→ 開く」ボタン付きで持っている**ので、導線は失われません。
- 暫定: `@media(max-width:520px)` で `min-width: 0` を消し、代わりに
  `flex-wrap: wrap` で2段に折り返させる。縦は増えるが誤タップは消える。

**根拠 ── 実測**

**実バグ: `--text-soft` が未定義のまま使われている**

```text
                                                    ▲
                                                    └─ 「集めさせて見せない」
                                                       ゲーム体験として最悪の裏切り
```

そして、これは**今後どの機能にも起きます**。
オトモン、ギルドPhase2-4、スキルツリー ── 機能が増えるほど、繋ぎ忘れの確率は上がります。

**だから、直すべきは2つの機能そのものではなく「繋ぎ忘れが起きない仕組み」です。**

`docs/architecture_review.md §4` の掟(7か条)に、**8か条目**を足すことを提案します:

```text
8. 新機能には必ず「入口」を書く。
   仕様書の冒頭に、この1行を必ず埋めること：

     ┌──────────────────────────────────────────┐
     │ 入口: ホーム → [　　　ボタン] → [　　　画面]  │
     │ タップ数: 　回（3回を超えるなら設計を見直す）  │
     └──────────────────────────────────────────┘

   埋められないなら、その機能はまだ作ってはいけない。
   （UNLOCK_DEFS に登録するだけでは「入口」にはならない。
     実際に押せるボタンが存在し、そのクリックハンドラが繋がっていること）
```

これは1行のルールですが、**装備・響く言葉の2件はどちらもこのチェックで止まっていました**。
`fgGo()`(`features.js:602-618`) が既に「機能への入口カタログ」として機能しているので、
**新機能は必ず `FG_CATEGORIES` + `fgGo()` に1行足す** を義務にすれば、
導きの妖精が自動的に「全機能の目次」になり、繋ぎ忘れが物理的に起きなくなります。
